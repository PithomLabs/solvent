# Plan 12: M2_TRANSCRIPT.md Generated-Artifact Lifecycle Fix

**Date:** 2026-09-15
**Status:** APPROVED — awaiting implementation
**Scope:** Fix the root cause of M2_TRANSCRIPT.md dirtying the working tree after every test run

---

## 1. Root Cause

`kernel/suite_test.go` `TestMain` unconditionally writes `docs/M2_TRANSCRIPT.md` after every test run (line 79). The `task test` command runs `go test -count=1 -p 1 ./...`, which includes `./kernel/`, triggering the regeneration. The file contains four nondeterministic fields:

| Field | Source | Changes every run |
|---|---|---|
| `generated_at` | `time.Now().UTC()` | Yes |
| `host` | `os.Hostname()` | Yes (per machine) |
| `dsn` | `testdb.Redact(dsn)` | Yes (per environment) |
| `elapsed_ms` | `c.Elapsed.Milliseconds()` | Yes |

The volatile section is wrapped in `<!-- volatile:begin -->` / `<!-- volatile:end -->` markers, but `task test` does not use these markers to strip the volatile content. Only `scripts/m0_accept.sh` strips volatile sections before comparing.

## 3. Generation Chain

```
task test
  → go test -count=1 -p 1 ./...
    → go test ./kernel/
      → kernel.TestMain
        → m.Run()
        → rec.writeTranscript("../docs/M2_TRANSCRIPT.md")
```

---

## 4. Why the File Changes

The `writeTranscript` method writes four nondeterministic fields into the `<!-- volatile:begin -->` / `<!-- volatile:end -->` section. The test results, receipts, and verdict are deterministic (same on every green run), but the volatile section changes every time.

---

## 5. Is This Intended?

Partially. The volatile markers indicate awareness that this section changes. But the file is tracked and the `task test` command regenerates it unconditionally, which contradicts the "frozen evidence" intent documented in README.md and review_fable.md.

---

## 6. Ownership Classification

**Generated evidence artifact** — tracked in Git, generated by tests, contains nondeterministic content. The correct model is: the file should only be regenerated through an explicit documentation/gate command, not as a side effect of ordinary test execution.

---

## 7. Lifecycle Contract

```
Ordinary test (task test):
    verify behavior
    MUST NOT mutate docs/M2_TRANSCRIPT.md

Explicit M2 gate (m2_accept.sh):
    regenerate evidence intentionally
    working tree may be dirty after — user decides whether to commit
```

---

## 8. Key Finding: m2_accept.sh Does NOT Manage the Transcript

The script runs `go test ./kernel/ -v -count=1` twice (lines 52, 80). Each run triggers `TestMain` → `writeTranscript`, regenerating the transcript as a side effect. The script then prints a summary (lines 98-102).

The script does NOT:
- restore the file after generation
- normalize the volatile section
- compare the file to a baseline
- commit the file
- clean up the file

**After running `m2_accept.sh`, the working tree WILL be dirty if timestamps/timing changed.** The script does not manage the file — it lets the test side effect leave the transcript in its regenerated state.

---

## 9. Recommended Fix

**Add an environment variable guard to `TestMain`** so transcript generation is opt-in.

Current behavior:
```go
// kernel/suite_test.go:79
if err := rec.writeTranscript(transcriptPath); err != nil {
```

Fixed behavior:
```go
if os.Getenv("M2_TRANSCRIPT") == "1" {
    if err := rec.writeTranscript(transcriptPath); err != nil {
```

Uses `== "1"` for precision (user preference). The ordinary `task test` run does NOT set this variable, so the transcript is not regenerated.
