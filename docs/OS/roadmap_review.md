I've read all three primary sources directly now, not the paraphrase, and the corrected account holds up. Specifically:

**The technical claim is sound, and I can see exactly why it's sound rather than just asserted.** `phase6.3_plan.md`'s original T-C9 was written expecting Conn1's commit to fail with `40001` — that was the team's stated hypothesis about how `SERIALIZABLE` + `NOT EXISTS` should behave. `phase6.4_plan.md`'s F-NEW records that when that exact test actually ran, the commit *succeeded* instead — the test's own name, `TestTC9_PartA_SerializablePredicateConflictEvidence`, is the evidence of a falsified prediction, not a designed-in negative control. That's the right way for this to have gone: a hypothesis was written down before it was tested, the test disagreed with the hypothesis, and it was treated as a CRITICAL finding requiring an architecture change rather than rationalized away. This is also a real, known category of subtlety in serializable-snapshot-isolation systems generally — whether a `NOT EXISTS` scan over an empty key range registers a read-set entry broad enough to conflict with a later insert into that range is implementation-dependent in ways that don't always match the naive theoretical guarantee, so this isn't an implausible thing to have discovered in practice.

**The fix is lower-risk than a novel mechanism would be, because it isn't one.** `FOR UPDATE` on `authority_target.target_id` is the exact lock pattern already used by `AttachJustification` and `Approve` to serialize against each other — extending it to two more operations is applying something already proven in this codebase, not introducing new locking behavior. And the two ordering proofs (Part A authorize-first, Part A2 revoke-first) use controlled multi-connection sequencing where the lock itself enforces the order — Conn2 structurally cannot proceed until Conn1 releases the lock — so there's no reliance on timestamp inference for those two; MVCC timestamp verification is reserved for Part B, the actual concurrent black-box test, which is where it's actually needed. That's the right test design, not an accidental one.

**H-1, M-1, M-2, M-3 from the original `phase4b_adv_review.md` are genuinely closed**, with named tests I can see cited with real output (`TestIntegration_AuthorizeAction_ActorIDMismatch` PASS, `TestLedger_AuthorizeAndCreateIntent_Allowed`/`_Denied` PASS), not just claimed closed.

Two small things worth doing, neither a blocker:

**No permanent negative control for the fixed vulnerability itself.** T-C10 is explicitly kept forever as a regression guard proving the old two-step *kernel-call* sequence is vulnerable. But the test that proved `SERIALIZABLE` + `NOT EXISTS` *alone* (without the lock) is insufficient — the F-NEW evidence itself — gets rewritten into the lock-based Part A rather than preserved separately. If a future refactor ever removes the `FOR UPDATE` acquisition while leaving everything else looking correct, nothing in the suite would catch that regression the way T-C10 catches a reversion to the two-step call pattern. Worth keeping the original predicate-only version as a permanent, deliberately-failing-if-the-lock-is-removed control, the same way T-C10 works for the other vulnerability class.

**Minor naming nit:** `sqlAttachJustificationLock` is now the lock used by four different operations, not just `AttachJustification`. Not a defect, just worth a rename (`sqlTargetRowLock` or similar) so the name doesn't actively mislead the next person reading it.
