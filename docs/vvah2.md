## Limitations, challenges, and flaws in evaluation, false alarms, and validation

### 1. No published accuracy numbers — self-acknowledged gap

The project explicitly states it has **no validated precision/recall figures**: "No published accuracy numbers yet. Precision/recall figures are not yet published." visa-vulnerability-agentic-harness:228-229  This is repeated verbatim in the features doc. visa-vulnerability-agentic-harness:232-232  The only "precision" metric available is an internal `verification_precision_pct` computed as `true_positive_count / raw_findings_count` — i.e. how much of the pipeline's own S4 output survives its own S6 verifier — not precision against any independent ground truth. visa-vulnerability-agentic-harness:427-434 

### 2. Findings are explicitly not confirmed vulnerabilities

The README states plainly: "Findings are triage candidates, not confirmed vulnerabilities — human review is required." visa-vulnerability-agentic-harness:221-222  This means the tool's output cannot be trusted as authoritative without a human validation step, undermining fully-automated use.

### 3. Non-determinism — results are not reproducible

Because the pipeline is LLM-driven, "two runs may differ" on the same target. visa-vulnerability-agentic-harness:221-222  This directly complicates evaluation: a benchmark score measured once may not generalize to the next run, and regression testing against fixed expected-output sets is inherently fragile.

### 4. Majority-vote false-positive filtering is disabled by default

The core FP-suppression mechanism — running S4 deep-dive N times at temperature > 0 and requiring a finding to appear in ≥ threshold runs — only works on `sdk`/`openai` backends with a temperature-capable model. The shipped default profile pins the deepdive role to a model that **rejects explicit temperature**, so voting silently collapses to a single pass: "Voting is effectively DISABLED by default... N identical-temp runs would just be N copies of one output (N× cost, 0 filtering)." visa-vulnerability-agentic-harness:26-33  The `cli` backend has no temperature control at all and always runs single-pass. visa-vulnerability-agentic-harness:223-225  This means the flagship "multi-agent voting" design pillar is often not actually active, and users must know to reconfigure it.

### 5. Fallback FP defenses are weaker/cruder

When voting is off, the pipeline falls back to: (a) a deterministic S5 prefilter (drops test/mock paths, hallucinated file paths, low self-rated confidence, missing evidence, trivial dups) visa-vulnerability-agentic-harness:18-34 , and (b) a single adversarial S6 verifier per finding that renders a binary TRUE/FALSE_POSITIVE verdict. visa-vulnerability-agentic-harness:57-108  Both are still LLM- or heuristic-based judgment calls rather than independently validated ground truth, and the S5 comment itself notes the model "ignores the prompt rule ~10%" of the time for test/mock path exclusion. visa-vulnerability-agentic-harness:22-23 

### 6. Verifier output can be ambiguous, and ambiguity handling has known past bugs

The S6 verifier's reply is parsed via regex for a `VERDICT:` line; if the model rambles without emitting a parseable verdict, this is an "unparseable" case. visa-vulnerability-agentic-harness:154-160  A code comment documents a fixed-but-notable flaw: unparseable verifier replies were previously miscategorized as confirmed `FALSE_POSITIVE`, which "understated true risk and skewed the precision metric" — now corrected to a distinct `VERIFY_ERROR` bucket, but this shows the precision metric has historically been vulnerable to silent distortion by parsing edge cases. visa-vulnerability-agentic-harness:164-173 

### 7. Guardrail-abort logic could mask systemic verifier failure vs. true absence of vulnerabilities

If ≥`guardrail_gate` verifier calls are blocked (e.g. by model safety guardrails) with zero confirmed findings, the whole run aborts with a `RuntimeError` — a defensive measure, but it also means a "clean" scan result and a "verifier is broken" result must be manually distinguished by the operator. visa-vulnerability-agentic-harness:124-148 

### 8. Severity/CVSS scoring is LLM-self-scored, not independently validated

CVSS 3.1 vectors are generated by the same LLM verifier that renders the TRUE/FALSE_POSITIVE verdict, with instructions to "Score the vector against the claimed impact even when returning FALSE_POSITIVE." visa-vulnerability-agentic-harness:103-104  There is no separate/independent scoring validation step; severity labels are mechanically derived from this self-reported vector band. visa-vulnerability-agentic-harness:230-230 

### 9. Dedup thresholds were empirically tuned, suggesting past miscalibration

The `step7_dedup.line_tolerance` config comment notes the prior default (10) was "too wide — collapsed distinct sinks in same method," now reduced to 3. visa-vulnerability-agentic-harness:225-225  This is evidence that deduplication — meant to reduce noise — previously caused real, distinct findings to be silently merged and lost (a false-negative risk introduced by the FP-reduction machinery itself).

### 10. Architecture context fed to the verifier "may be incomplete or stale"

The S6 verifier prompt itself warns that the call-graph/entry-point/design-control context "may be incomplete or stale," and instructs the model to re-derive ground truth via Read/Grep rather than trust it. visa-vulnerability-agentic-harness:300-304  This is a structural admission that upstream stages (S1 call-graph construction, S2 threat modeling) can themselves be wrong, and verification quality depends on the verifier successfully overriding that flawed context rather than being misled by it.

### 11. Elevated privilege and trust assumptions complicate safe validation

The tool "runs with elevated privilege and must only be used against trusted repositories by authorized operators; running it against untrusted input without the recommended hardening controls may expose host credentials, API keys, and sensitive files to exfiltration or pipeline bypass." visa-vulnerability-agentic-harness:230-233  This is a security/operational limitation rather than a strict "evaluation" one, but it constrains how and where the tool's output can be safely validated at scale (e.g., you cannot casually point it at arbitrary/untrusted third-party code for benchmarking without hardening).

### Summary

The codebase is candid about its own limitations: it is a non-deterministic, LLM-generated triage tool with **no published precision/recall benchmark**, whose primary anti-false-positive mechanism (majority voting) is silently disabled under the shipped default configuration, leaving a single deterministic prefilter and a single adversarial verifier pass as the actual FP defense. visa-vulnerability-agentic-harness:226-232  Several of the mitigations for these gaps (dedup tolerance, verdict-parsing error handling) show a history of empirical tuning after real miscalibration was discovered, indicating the evaluation/validation machinery is still maturing rather than settled.

## Q2
how does Solvent can help based on your reply above? # Solvent

A transactional belief ledger for autonomous agents. The database — not the LLM — decides whether an
action is allowed.

**Live demo: https://byb43s8nh2.us-west-2.awsapprunner.com/demo**  
**Demo video: https://www.youtube.com/watch?v=EtFUaCnbHPA**

Also live: [`/proof`](https://byb43s8nh2.us-west-2.awsapprunner.com/proof) (the control experiment)
and [`/ledger`](https://byb43s8nh2.us-west-2.awsapprunner.com/ledger) (read-only ledger).

![Solvent](solvent.png)

## What Solvent is

Persistent memory for evidence, authority, and change, built around one separation:

```text
Memory / Retrieval
       ↓
Belief
       ↓
Authority
       ↓
CockroachDB invariant
```

> **Retrieval and judgment are allowed to be wrong. Authority is what the database constrains.**

An agent searches memory, cites what it relied on, and forms a belief. That belief carries *debt* —
review obligations that must be discharged before it can be promoted. Only a promoted belief can
authorize an action. When the belief is later invalidated, the database refuses to let the
authorization outlive it.

## Why ordinary RAG is insufficient

Retrieval returns what is nearest, not what matters. Usually those overlap; when they don't, nothing
in the pipeline notices — and the authority to act was granted by the same context window that
produced the answer. There is no durable boundary between evidence, belief, and permission.

Solvent does not claim better retrieval. It claims that retrieval must not silently become authority.

## Architecture

```text
Judge's browser
      ↓  HTTPS
AWS App Runner  us-west-2       Go binary, no framework, ~25 MB image from ECR
      ├──────→ Amazon Bedrock   amazon.titan-embed-text-v2:0, 1024-d, via an instance role
      ↓  pgx
CockroachDB Cloud Serverless    v26.2.5 · multi-region · primary region aws-us-west-2
```

![Architecture](architecture.png)

App Runner's region and the cluster's primary region are the same, so no request in the demo path
pays a cross-region round trip. `task deploy` refuses to deploy if that stops being true.

Seven tables in two layers: the four frozen ledger tables (`belief`, `belief_edge`, `evidence`,
`action_intent`) and the corpus/wizard layer (`corpus_issue`, `belief_corpus_citation`,
`refusal_log`). The kernel is domain-agnostic Go; the wizard is one embedded HTML file and a handful
of handlers.

## The measured retrieval finding

This is a measured limitation, not a caveat, and it is why the product is shaped this way.

Ask the corpus the question an engineer would actually ask before a deployment:

```text
"Is etcd v3.5.x safe to deploy?"
  #19220  0.372424   go.etcd.io/etcd/client/v3 updates
  #12987  0.387913   3.4 to 3.5 upgrade may panic
  #12788  0.401092   Using client in v3.5.0 and etcd server with v3.4.14
```

Plausible, on-topic, and it does not contain the incident that matters. Ask about integrity instead:

```text
"etcd v3.5 data inconsistency after upgrade"
  #14139  0.199509   inconsistent data in etcd 3.5.4
```

`0.199509` against `0.372424`. The embedding is behaving correctly — a deployment-phrased question is
simply nearer to release-process material than to defect reports. **An agent that asks "is this safe
to deploy?" and reads the top-k will not see the incident that matters most.**

The canonical incident is worse. `#13766 · Inconsistent revision and data occurs`, the issue that
actually destroys the claim, sits at distance `0.594920` from it — a measured **rank 573 of 7,239**.
No top-k, threshold or reranker puts that in front of a judge.

> That rank is an offline measurement, not something the application renders. On screen the issue is
> introduced by URL and the UI says so: *"Not retrieved — introduced by URL."*

The response is not to tune the retrieval. It is to stop treating retrieval as an authority:

> Retrieval proposes candidates. It decides nothing. The database decides.

A demo where the human reasons correctly and the database never has to intervene would demonstrate
nothing.

## Database enforcement

Three schema-level mechanisms carry the entire guarantee:

```sql
-- 1. Debt must be empty before a belief can be promoted.
CHECK (status <> 'promoted' OR debt = '{}')          -- promoted_is_debt_free -> 23514

-- 2. An intent may only cite a belief that is promoted RIGHT NOW.
FOREIGN KEY (belief_id, belief_status)
  REFERENCES belief(id, status) ON UPDATE CASCADE     -- gate -> 23503

-- 3. And a live intent may not survive its belief losing that status.
CHECK (state <> 'live' OR belief_status = 'promoted') -- live_requires_promoted -> 23514
```

The third only works because of a property we measured rather than assumed: **CockroachDB
re-evaluates `CHECK` constraints on rows modified by `ON UPDATE CASCADE`.** Retracting a belief
cascades the new status into every citing intent, and the `CHECK` on those rows then refuses the
whole transaction. The application never checks this. It cannot forget to.

**On `belief_edge` and traversal.** CockroachDB does not traverse `belief_edge`. The recursive walk
is a `WITH RECURSIVE` CTE in application code. **Belief traversal is application logic; CockroachDB
enforces the invariant at the authority boundary.** That distinction matters if you are reading
`db/001_schema.sql` looking for the graph logic — it is not there, and it is not supposed to be.

## Control experiment

The same race, the same correct application logic, three schemas. Served at

| 2    | naive    | `SERIALIZABLE`   | `40001 RETRY_SERIALIZABLE`                        | local, v26.2.0            |

Two readings the transcripts insist on:

* **`40001` is a retry signal, not a refusal.** The harness deliberately does not retry, so the raw
  code is visible. Under `crdb.ExecuteTx` the transaction retries and *then* refuses on fresh state.
  The accurate chain is **detect → retry → refusal on fresh state**.
* **Cell 1 was observed, not predicted.** The anomaly was inherited from a PostgreSQL-era claim and
  had never been run against CockroachDB. It reproduced. The corruption came from the schema, not
  from a logic bug.

## Formal model

`formal/lean/` contains a **Lean 4 + Mathlib formal model** of Solvent's belief/authority state
machine.

It machine-checks that the core authority invariants are preserved by the successful abstract
state transitions:

* `promote_preserves_validity`
* `cancelIntent_preserves_validity`
* `authorizeIntent_preserves_validity`
* `retractCascade_preserves_validity`

It also proves the central authority properties:

* `live_intent_implies_promoted`
* `no_live_intent_on_retracted_belief`

and the layered promotion/cascade properties:

* `promotion_updates_dependent_intent`
* `cascade_retraction_updates_dependent_intent`
* `cascade_retraction_cannot_leave_live_intent`
* `cascade_update_preserves_gate`
* `cascade_retraction_blocks_live_intent`

The Lean model uses the same core vocabulary as the schema — beliefs, debt, intents, statuses, and
belief dependencies — and is pinned to Lean 4.33.0 with a specific Mathlib revision.

The formalization is intentionally scoped:

> **Lean proves the abstract state-machine preservation properties. CockroachDB proves the real engine's
> refusal behavior empirically.**

This is **not** a machine-checked refinement proof of the Go/CockroachDB implementation.

Build the formal model with:

```bash
cd formal/lean
lake build
```

The formal modules contain zero `sorry`, zero `admit`, and zero unchecked `axiom`.

### Answer

(2) The indexed harness codebase still shows the 9-stage pipeline (`s1`–`s9` ending at SARIF export) visa-vulnerability-agentic-harness:42-51 ; the article's stages 10/11 (remediate/adversarial-validation-panel) and MTTA aren't present in what I can search, so the design plan below targets the pipeline as it actually exists plus the write-path gap the article describes.

## Design plan: wiring Solvent's belief/authority model onto VVAH

**1. Model each finding as a belief with typed debt, not a report row.**
Today a finding moves through `s4`(raw) → `s5`(prefiltered) → `s6`(verified TRUE/FALSE_POSITIVE + CVSS) → `s7`(canonical) purely as data mutated in-process and checkpointed to pickle visa-vulnerability-agentic-harness:165-211 . Recast each stage transition as a debt item on a Solvent-style belief: `s6_verified`, `s7_deduped`, `human_reviewed`, and — if remediation is added — `build_passed`, `exploit_retested`, `code_reviewed`. A finding can only reach a `promoted` status (i.e., become something CI/merge tooling is permitted to act on) once every debt item is discharged, enforced the way Solvent enforces it: `CHECK (status <> 'promoted' OR debt = '{}')`. This turns the README's "human review is required" from prose visa-vulnerability-agentic-harness:221-222  into a schema-level fact no caller can bypass.

**2. Put the merge/patch-apply action behind a foreign-key gate, not a doc.**
For the write path the article describes (stage 10 writing candidate fixes, stage 11 scoring them), model "patch is mergeable" as an `action_intent` row that may only cite a belief that is `promoted` *right now* — Solvent's `FOREIGN KEY (belief_id, belief_status) REFERENCES belief(id, status) ON UPDATE CASCADE`. If a later run or a build failure retracts the belief (e.g. re-test shows the exploit still lands), the cascade + `CHECK (state <> 'live' OR belief_status = 'promoted')` invariant makes it structurally impossible for a stale "validated" patch to remain a live merge candidate, closing exactly the gap Wilson raised: an authorization gate that lives outside the model.

**3. Make voting a debt-discharge condition with a quorum, not silent single-pass.**
`s4_deepdive`'s majority vote already reports "V of N runs agreed" in the finding metadata visa-vulnerability-agentic-harness:41-54 , but collapses to N=1 silently when the model rejects `temperature`. In this model, the vote count becomes a quantitative debt-discharge requirement (e.g. `votes >= vote_threshold OR deterministic_prefilter_passed`), and if voting has collapsed to 1, the belief simply cannot discharge that debt item — it stays undischarged/un-promotable rather than quietly passing under a weaker guarantee.

**4. Treat checkpoint corruption/mismatch the way VVAH already treats untrusted deserialization, and reuse that pattern as the evidence-ingestion boundary.**
VVAH already has a real authority-boundary pattern worth reusing directly: checkpoints are loaded through a `_RestrictedUnpickler` that allow-lists only the tool's own classes and a small stdlib set, refusing (not crashing on) anything else and simply re-running the stage visa-vulnerability-agentic-harness:48-63 visa-vulnerability-agentic-harness:82-104 . Any Solvent integration that ingests VVAH's SARIF/checkpoint output as "evidence" should apply the same allow-list discipline at the ingestion boundary rather than trusting the on-disk artifact as-is.

**5. Make MTTA a ledger query, not a self-reported number.**
Record `discovered`, `verified`, `promoted`, `merged`, and `retracted` as immutable, timestamped ledger events per belief. MTTA per the harness's own "elapsed time from AI-discovered exploitability to a validated fix" definition becomes `merged_ts - discovered_ts` computed from rows that can't be edited after the fact, and a later retraction (regression) is visible in the ledger rather than leaving a stale "resolved" label — directly answering the article's "one metric, three definitions" complaint.

## Insights this exercise surfaces for improving Solvent itself

- **Quorum-typed debt, not just boolean debt.** VVAH's "V of N runs agreed" confidence model suggests Solvent's debt items could carry a quantitative discharge condition (N-of-M independent evidence sources agree) rather than a single citation satisfying a debt item outright. This generalizes "the database decides" from a boolean gate to a statistical one, closer to how real security/ops judgment actually works.
- **A first-class "degraded" provenance flag.** VVAH's SARIF output explicitly marks a run degraded when a stage failed (`executionSuccessful=false`, per-stage `invocations[]`) rather than silently reporting partial results as complete visa-vulnerability-agentic-harness:87-90 . Solvent's belief model, as described, doesn't appear to distinguish "formed from complete evidence collection" from "formed after a retrieval/tool failure." Adding a degraded/partial-evidence provenance tag on beliefs — separate from confidence — would let promotion logic (or auditors) apply extra scrutiny to beliefs formed under incomplete search, which the README doesn't currently describe.
- **Deterministic vs. LLM-attested debt items as distinct classes.** VVAH cleanly separates deterministic stages (`s5` prefilter, `s9` SARIF) from LLM stages in its own docs visa-vulnerability-agentic-harness:61-76 . Solvent could formalize the same split for debt items — a "build passed" discharge is deterministic and verifiable by the database's own record of a CI callback, whereas "reviewer read the diff" is attested, not provable. Requiring a minimum number of *deterministic* discharges (not just "debt=empty" regardless of kind) before promotion would raise Solvent's bar beyond what the README currently describes.
- **Redaction at the evidence-write boundary.** VVAH masks card/PII/credential material specifically at the point reports are written to disk visa-vulnerability-agentic-harness:98-107 . If Solvent's `evidence` table stores raw cited text (e.g. snippets from a corpus or logs), it's worth checking whether it has an analogous redaction boundary — the README doesn't mention one, and an immutable ledger that has ingested a secret is a worse problem than a mutable one.
- **Config-driven backend swapping as a model for embedding-provider agnosticism.** VVAH's per-role `{id, via}` backend config, extended in the article to be provider-agnostic for remediation/validation, is the same lesson Solvent's own architecture note about Bedrock Titan v2 implicitly invites: keeping the embedding/judgment layer swappable via config protects against a single-provider dependency, which matters given Solvent's own admission that it hasn't measured index distribution/sharding claims.

None of these are things I can confirm Solvent's actual code already does or doesn't do — they're inferences from the gap between VVAH's documented patterns and what the pasted README describes. Verifying which of these Solvent already has would require read access to its repository.

class _RestrictedUnpickler(pickle.Unpickler):
    """Unpickler that only reconstructs the pipeline's own model classes and a
    small allow-list of safe stdlib primitives — never os/subprocess/builtins
    callables that a malicious checkpoint would use for code execution."""

    def find_class(self, module: str, name: str):
        if module == "vvaharness" or module.startswith("vvaharness."):
            return super().find_class(module, name)
        if module == "builtins" and name in _SAFE_BUILTINS:
            return getattr(builtins, name)
        allowed = _SAFE_IMPORTS.get(module)
        if allowed and name in allowed:
            return super().find_class(module, name)
        raise pickle.UnpicklingError(
            f"refusing to load disallowed checkpoint object {module}.{name}")

def load_ckpt(ckpt_dir: Path, run_id: str, step: str):
    p = _ckpt_path(ckpt_dir, run_id, step)
    if not p.exists():
        return None
    try:
        with open(p, "rb") as f:
            obj = _RestrictedUnpickler(f).load()
    except (pickle.UnpicklingError, EOFError, ValueError,
            ModuleNotFoundError, ImportError, AttributeError) as e:
        # Three cases degrade the same safe way — re-run the step instead of
        # crashing or executing untrusted bytes:
        #   * corrupt / truncated file (EOFError, UnpicklingError);
        #   * checkpoint written by a different tool version whose model
        #     classes have moved/renamed (ModuleNotFoundError/ImportError/
        #     AttributeError);
        #   * a tampered checkpoint referencing a disallowed class, which the
        #     restricted unpickler rejects with UnpicklingError BEFORE the
        #     object is reconstructed (so no __reduce__ gadget can fire).
        print(f"  [ckpt] WARN: {p.name} is unreadable, version-mismatched, or "
              f"untrusted ({e}); ignoring and re-running {step}", file=sys.stderr)
        return None
    print(f"  [ckpt] resumed {step} from disk", file=sys.stderr)
    return obj
